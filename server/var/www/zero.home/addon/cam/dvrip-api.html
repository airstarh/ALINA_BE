Important: DVRIP is a binary TCP protocol, not a browser REST API. The browser talks to the server; the server holds credentials and connects to the camera. Never place camera passwords or Sofia hashes in this page or in client-side JavaScript.

Scope and terminology

DVRIP and NETIP are names commonly used for the proprietary protocol implemented by these Xiongmai-family devices. This page describes operations verified in the current PHP client, not every command a particular firmware may implement.

Raw camera protocolBinary framed TCP, normally port 34567; JSON payload inside each frame.
Application protocolSame-origin HTTP JSON actions in stuff/php/api.php.
Separate protocolsRTSP carries media; ONVIF supplies discovery/PTZ/accounts on supported cameras.

Transport

Framing20-byte little-endian header followed by JSON bytes ending in \n\0.

Packet format

The current codec emits this 20-byte header (C/PHP pack notation):

CCx2VVx2vV marker : 0xff version : 0 or 1 session : uint32 little-endian sequence: uint32 little-endian message : uint16 little-endian length : uint32 little-endian payload: UTF-8 JSON object + LF + NUL

For an ordinary request, the response keeps the sequence and uses the request message ID plus one (for example 1000 → 1001, 1040 → 1041). After login, the response session must match the assigned session ID. The implementation rejects mismatched identity, malformed JSON, missing terminators, and oversized payloads.

Authentication

TCPmessage 1000 — loginresponse 1001
{ "EncryptType": "MD5", "LoginType": "DVRIP-Web", "PassWord": "<SofiaHash(password)>", "UserName": "<camera user>" }

A successful response contains Ret (normally 100, 150, or 515) and a hexadecimal SessionID, for example 0x00000001. The clear password is never returned by the camera.

Verified message catalogue

These are the message IDs currently used by the project. A firmware can reject a command even when the ID is known.

TCP1020 — read informationresponse 1021

Named reads such as SystemInfo. The same mechanism is used for other informational objects requested by the client.

TCP1020 — SystemInforesponse 1021

Returns the system-information branch used to identify the device and firmware.

TCP1360 — capability readresponse 1361

Named capability reads: SystemFunction, EncodeCapability, and Camera. These values drive supported editor options and capability gating.

TCP1042 — read configurationresponse 1043

Send Name, SessionID, and return the requested named branch, for example Network.NetCommon, Simplify.Encode, Camera.Param, or Uart.PTZ.

TCP1040 — write configurationresponse 1041

Send the complete merged branch under the same Name, plus SessionID. The app reads the latest branch first, changes only selected fields, writes it, then reads back and verifies it. One OEM port save may return 603 while still storing the value; listener verification handles that case.

TCP1450 — rebootresponse 1451

Name: OPMachine, OPMachine: {Action: Reboot}. The server waits for the configured reboot hold time and closes the connection.

TCP1400 — PTZ preset operationresponse 1401

Name: OPPTZControl with Command GotoPreset, SetPreset, or ClearPreset. The current live PTZ direction/zoom implementation prefers ONVIF when available; this DVRIP preset call is retained for verified preset operations.

TCP1636 — email testresponse 1637

Name: OPMailTest and an OPMailTest settings object.

TCP2008 — FTP testresponse 2009

Name: OPFTPTest and an OPFTPTest settings object.

These are camera-user operations. ONVIF users are a separate ONVIF account store where the device exposes one. Existing passwords are not readable; blank “new password” fields preserve them unless the explicit empty-password action is selected.

Talkback extension

Talkback uses the same DVRIP framing but a separate control/media arrangement. One browser talk session therefore involves three logical connections:

  1. The browser opens one authenticated application WebSocket at /cam-talk.
  2. The server opens DVRIP TCP socket 1 to log in and send Start/Stop control messages.
  3. The server opens DVRIP TCP socket 2 to claim the talk channel and carry binary audio media.

The microphone bytes travel browser → application WebSocket → server → DVRIP media socket 2. The browser does not open either DVRIP socket and never needs direct camera access. Closing the browser WebSocket closes both camera-side sockets and sends Stop when possible.

MessagePurpose
0x059a → 0x059bClaim the talk channel (OPTalk).
0x0596 → 0x0597Start or stop talk control.
0x0598Binary media: 320 bytes of G.711 A-law per frame, 8 kHz, 8-bit, mono.
0x0599Camera media response drained by the server.

The browser only receives a short-lived authorization token and connects to the server WebSocket /cam-talk; it never receives DVRIP credentials.

Application HTTP API

The PHP wrapper is stuff/php/api.php. Responses use {ok, data, error}; configuration-changing actions require POST. The camera query value is a configured camera ID.

Implementation and safety rules

  • Read the latest camera branch before writing; merge only fields represented by the editor.
  • Write a complete branch, then read it back and verify the requested values.
  • For service-port changes, reconnect and verify the new listener; revert to the previous value if verification fails.
  • Treat camera-reported capabilities and option lists as authoritative for that camera. A known message ID does not guarantee firmware support.
  • Keep credentials server-side. This static reference intentionally contains no configured hostnames, passwords, hashes, or tokens.
  • Do not confuse camera DVRIP users with ONVIF users; the two stores can be separate and can have different roles.
